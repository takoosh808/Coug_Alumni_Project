# Alumni Database Schema

This document describes the tables currently initialized by `db.py`. SQLite uses type affinity, so `BOOLEAN` values are stored as integer `0`/`1`, and timestamps use SQLite's `TIMESTAMP` affinity. The same tables are also designed to work with the configured PostgreSQL backend.

## IV.2.1.1. Alumni Table

**Table: `alumni`**

Stores alumni profile information and engagement-questionnaire responses. CSV ingestion matches records by email: an existing email is updated; a new email inserts a row. The database schema declares email as unique, but does not declare it `NOT NULL`; the ingestion process skips rows with blank email values.

| Column | SQLite type | Constraints / default | Description |
|---|---|---|---|
| `id` | INTEGER | Primary key; auto-increment | Internal identifier for an alumni record. Excluded from CSV downloads. |
| `first_name` | TEXT | Nullable | Alumni first name. |
| `last_name` | TEXT | Nullable | Alumni last name. |
| `email` | TEXT | UNIQUE; nullable in the DDL | Email address used to match CSV records. |
| `current_company` | TEXT | Nullable | Alumni's current company. |
| `graduation_year` | INTEGER | Nullable | Year the alumnus graduated. |
| `major` | TEXT | Nullable | Alumni major or field of study. |
| `linked_in` | TEXT | Nullable | LinkedIn profile URL or value. |
| `q_internship` | TEXT | Nullable | Response to the internship-opportunities question. |
| `q_guest_lecture` | TEXT | Nullable | Response to the guest-lecture question. |
| `q_capstone_mentor` | TEXT | Nullable | Response to the capstone-mentoring question. |
| `q_company_visits` | TEXT | Nullable | Response to the company-visits question. |
| Additional questionnaire fields | TEXT by default | Nullable; column added when ingested | New CSV columns are added dynamically. `graduation_year` is created as INTEGER when applicable. |

## IV.2.1.2. Application User Table

**Table: `app_users`**

Stores login identities, password hashes, authorization roles, account status, and account timestamps. Passwords are stored as salted scrypt hashes, never plaintext. User accounts are separate from alumni profile records.

| Column | SQLite type | Constraints / default | Description |
|---|---|---|---|
| `id` | INTEGER | Primary key; auto-increment | Internal identifier for an application account. |
| `username` | VARCHAR(80) | NOT NULL, UNIQUE | Username accepted for sign-in. |
| `email` | VARCHAR(255) | NOT NULL, UNIQUE | Email accepted for sign-in. |
| `password_hash` | VARCHAR(255) | NOT NULL | Salted scrypt password hash. |
| `role` | VARCHAR(30) | NOT NULL; default `'user'` | Application role. The app accepts `user` or `admin` when accounts are created or edited. |
| `is_active` | BOOLEAN | NOT NULL; default `TRUE` | Whether the account is allowed to sign in. SQLite stores this as integer `1` or `0`. |
| `created_at` | TIMESTAMP | NOT NULL; default `CURRENT_TIMESTAMP` | Account creation time. |
| `updated_at` | TIMESTAMP | NOT NULL; default `CURRENT_TIMESTAMP` | Account update time. The account-management operation refreshes this when an account is edited. |
| `last_login_at` | TIMESTAMP | Nullable | Time of the most recent successful login. |

## Relationships and Implementation Notes

- The current schema defines no foreign-key relationship between `alumni` and `app_users`; they represent separate kinds of records.
- `alumni.email` and `app_users.email` are each unique within their own table. They do not reference one another.
- SQLite uses `INTEGER PRIMARY KEY AUTOINCREMENT` for these IDs. PostgreSQL uses `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`.
- The `app_users.role` allowed values are validated by the application; the current table definition does not add a database-level `CHECK` constraint.
- There are no checkout, checkout-message, or asset tables in the current application schema.
